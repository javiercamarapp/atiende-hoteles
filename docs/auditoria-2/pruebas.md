## Hallazgos

### [ALTO] El resumen de caja del night audit (`cargosPorConcepto`/`pagosPorMetodo`) da vacío en el caso de uso normal — 0% de cobertura de prueba, verificado roto sin tocar código
`apps/api/src/jobs/nightAudit.ts:97-108`

Escenario: `runNightAudit` postea correctamente el cargo de hospedaje (`postedCharges`, construido en memoria durante el loop — correcto y sí probado), pero después arma el resumen de caja con dos queries que filtran por `created_at::date = $2::date` (`params.businessDate`, líneas 97-108). El problema: `charge.created_at`/`payment.created_at` son `timestamptz not null default now()` (`packages/db/migrations/0007_folio.sql:30`) — la hora REAL de inserción, no la fecha de negocio que se está auditando. Un night audit corrido el 2026-09-06 para `businessDate="2026-09-10"` (mismo patrón de fecha "futura respecto al reloj real" que usan los propios tests oficiales del archivo, `tests/integration/revenue/night-audit.spec.ts:38,64,95,115`) inserta el cargo con `created_at::date = 2026-09-06`, pero la query del resumen busca `created_at::date = 2026-09-10` → 0 filas. Lo reproduje con una prueba temporal (idéntica en estructura a las oficiales, borrada al terminar): `postedCharges` trae el cargo de $1200 real; `cargosPorConcepto` devuelve `{}`. Esto no es un caso de laboratorio: es el patrón operativo NORMAL de un night audit real (correrlo después de medianoche para el día de negocio que acaba de cerrar, donde `businessDate` — "ayer" — casi nunca coincide con la fecha de reloj del proceso que audita — "hoy"). Ninguno de los 5 tests de `night-audit.spec.ts` afirma nada sobre `cargosPorConcepto`/`pagosPorMetodo` (confirmé con `grep -n "cargosPorConcepto\|pagosPorMetodo" tests/`: cero resultados fuera de mi prueba temporal); ambos campos sí están tipados y expuestos en `apps/web/src/lib/api.ts:558-559` (destinados al panel de "Cierre diario" de Back-office) pero **todavía no se renderizan en ningún `.tsx`** — confirmé con `grep` que hoy no hay consumidor visible, lo que limita el radio de exposición actual pero no lo vuelve inofensivo: es la clase exacta de bug que se "activa" el día que alguien conecta el campo a la UI, sin que ningún test lo detecte antes.

Consecuencia: cuando este campo se conecte a la UI (ya está en el tipo del cliente API, a un PR de distancia), el gerente vería el reporte de cierre de caja del día en $0 pese a que sí se cobró — exactamente el escenario que un night audit existe para prevenir (detectar faltantes de caja). Hoy el radio de impacto es cero porque nadie lo lee, pero es dinero mal calculado en silencio con 0% de cobertura, el patrón "4 o menos: la suite pasa con la función rota" que este mismo rubro usa como piso.

Causa raíz probable: la query de resumen usa `created_at` (momento de inserción) en vez de la columna correcta para agrupar por fecha de negocio — `stay_date` para cargos de hospedaje (que sí existe, `packages/db/migrations/0030_folio_engine.sql`) o `params.businessDate` como constante fija, no una comparación contra una columna de timestamp de inserción.

### [ALTO] Ninguna prueba oficial cubre la doble confirmación concurrente de una aprobación de dinero — el único camino de dinero del sistema sin el guardarraíl (advisory lock/UPDATE atómico) que tienen todos los demás
`packages/agent-core/src/postgresApproval.ts:153-203` (`PostgresApprovalQueue.decide`) — `apps/api/src/lib/aprobacionEjecutor.ts:38-40`

Escenario: `decide()` sigue el patrón lee-decide-en-JS-escribe: `fetchRowOrThrow` (un `SELECT` plano, sin `FOR UPDATE`) → valida en JavaScript que `status === 'pendiente'` y que el actor/rol no haya confirmado ya (comparando contra `loadConfirmations`, otro `SELECT` plano) → `insertConfirmation` → cuenta confirmaciones en memory y, si alcanza el umbral, un `UPDATE ... set status = 'aprobada'` **sin cláusula `WHERE status = 'pendiente'`** que lo haga condicional/atómico. No existe ningún `UNIQUE` en `agent_approval_confirmation (approval_id, actor)` ni `(approval_id, role)` que el motor de Postgres pudiera usar para rechazar una fila duplicada por su cuenta; el único advisory lock de este archivo (`lock_agent_approval_key`, `packages/db/migrations/0042_agent_approval.sql:60`) protege la CREACIÓN de una solicitud nueva, no la fase de `decide()`. Esto es el mismo patrón de carrera que causó el CRÍTICO original de tool-calling en `docs/auditoria-1/tool-calling.md` (corregido ahí para la generación de IDs de aprobación, no para esta fase de decisión). `apps/api/src/lib/aprobacionEjecutor.ts:38-40` ejecuta la tool (`tool.run(ctx, parsed.data)`) de forma incondicional en cuanto `decided.status === "aprobada"` — si dos llamadas a `decide()` concurrentes (p. ej. el mismo owner haciendo doble clic en "aprobar" desde el panel web, o aprobando desde el panel web Y desde el botón de WhatsApp — REQ-UX-006 agrega justo ese segundo canal — casi al mismo instante) ambas leen `pendiente` antes de que cualquiera confirme, **ambas** ejecutarían la tool de dominio (p. ej. `autorizar_gasto_mantenimiento`, que cierra un ticket con un costo autorizado). Intenté reproducir esta carrera empíricamente 6 veces seguidas con `Promise.all` sobre el endpoint HTTP real (mismo patrón que sí destapó la carrera de Idempotency-Key en la ronda 1) y **no logré que ambas ejecutaran** — la segunda siempre llegó tarde y recibió 409 "ya no está pendiente", probablemente porque el proceso de `decide()` es demasiado corto para que el entrelazado ocurra dentro de la misma máquina/proceso de prueba. Esto no descarta el riesgo: la ausencia del mismo guardarraíl (lock/UPDATE condicional) que SÍ existe en cada otro camino de dinero del sistema (reserva, folio, pago, timbrado, night audit) es en sí misma la brecha de prueba/diseño — nadie escribió el test que fuerce el entrelazado real (p. ej. con una pausa artificial inyectada, como sí hicieron para el hash chain de `audit_log` en auditoría-1/correccion-bd), así que hoy no hay evidencia de que el camino sea seguro bajo latencia de red real (dos servidores, o WhatsApp+panel web en paralelo), solo de que no se rompe con dos llamadas en el mismo proceso Node.

Consecuencia: si la carrera se materializa en producción, una acción de dinero aprobada por doble confirmación (gasto de mantenimiento, mensaje transaccional, lo que sea que se cablee detrás de `needs_approval` en el futuro) se ejecuta dos veces con una sola aprobación real — el mismo tipo de daño (efecto duplicado) que REQ-QA-004 exige prevenir explícitamente para dinero.

Causa raíz probable: `decide()` se escribió replicando el patrón de la cola en memoria (`InMemoryApprovalQueue`, donde JS de un solo hilo sí hace el check-then-act atómico gratis) sin adaptar la fase de decisión al patrón de concurrencia real de Postgres que sí se aplicó en cada otro módulo de dinero de este mismo sprint (H4/H5/H8).
