## Hallazgos

### [CRÍTICO] El total de una reserva multi-noche no tiene ninguna prueba que verifique el monto exacto — un bug de -50% de ingreso pasa toda la suite en verde
`apps/api/src/routes/reservas.ts:160-176` (cálculo) — `tests/integration/api/reservas-y-folios.spec.ts:41-67` (única prueba que toca este camino)

Escenario: una reserva GM de Hotel Demo Centro, tipo "Estándar" ($1,200 MXN/noche según `packages/db/src/seed.ts:59`), del 2026-09-10 al 2026-09-12 (2 noches) debería totalizar $2,400. Cambié la línea 175 de `totalAmount += rateRows[0] ? Number(rateRows[0].price) : 0;` a `totalAmount = rateRows[0] ? Number(rateRows[0].price) : 0;` (asignación en vez de acumulación — el típico error de "guardé mal el operador"), de modo que una reserva de 2 noches cobra $1,200 en vez de $2,400. Corrí `npm run test:integration` (19/19 verde) y `npm run test:adversarial` (28/28 verde) con el bug puesto, luego revertí el archivo y confirmé con `diff` que quedó idéntico al original. La única aserción sobre el total en `tests/integration/api/reservas-y-folios.spec.ts:53` es `expect(created.total).toBeGreaterThan(0);` — no compara contra el monto exacto esperable desde el fixture de `rate_plan` sembrado.

Consecuencia: el hotel factura de menos en cada reserva multi-noche (aquí, -50% en una reserva de 2 noches; el patrón empeora con más noches si el bug fuera, por ejemplo, "solo cuenta la primera noche" en vez de sumar) y nadie se entera porque la suite completa —117 unit + 19 integración + 28 adversarial— queda en verde. Es exactamente el escenario "3-4: existe un camino donde el producto hace algo mal (tarifa inventada/incorrecta) y nadie se entera" de la escala del rubro.

Causa raíz probable: la prueba de integración fue escrita para probar que el flujo completo (reserva→outbox→audit) no truena, no para anclar el valor de negocio (`monto = Σ rate_plan.price` por noche).

### [ALTO] Ninguna prueba dispara dos requests concurrentes con la MISMA Idempotency-Key contra un endpoint de dinero (el escenario real de doble-cobro por doble-clic)
`apps/api/src/lib/idempotency.ts:31-78` — `tests/integration/api/reservas-y-folios.spec.ts:69-92`

Escenario: el comentario de `idempotency.ts:1-9` afirma explícitamente que el patrón `INSERT ... ON CONFLICT DO NOTHING` "da, gratis, la serialización correcta bajo concurrencia real" cuando dos requests con la MISMA `Idempotency-Key` llegan en paralelo (el caso real: un huésped hace doble-clic en "pagar" o el frontend reintenta una request que sí llegó). La única prueba que ejercita esa ruta (`reservas-y-folios.spec.ts:69-92`, "misma Idempotency-Key + mismo cuerpo") dispara los dos requests **secuencialmente** (`await first; ... await second`), nunca con `Promise.all`. Escribí un test temporal disparando 2 `POST /hoteles/:id/folios/:id/pagos` en paralelo con la misma clave contra `embedded-postgres` real: el mecanismo sí resistió (1 solo `payment` insertado), pero **la suite entregada no prueba esto en absoluto** — si una futura refactorización de `withIdempotency` (p. ej. mover el `INSERT` de la llave después de `run()`, o cambiar `ON CONFLICT DO NOTHING` por un `SELECT` previo no atómico) reintrodujera una carrera, ningún test lo detectaría hasta que ocurriera en producción como un cargo duplicado real a un huésped.

Consecuencia: el huésped puede terminar con un cargo duplicado en su tarjeta si una regresión futura rompe la serialización; el hotel/gerente absorbe la disputa y el contracargo. Es justo el tipo de hallazgo que REQ-QA-004 ("existe aprobación humana en acciones irreversibles... antes de mergear") y el ancla del rubro ("las pruebas de concurrencia corren contra embedded-postgres") esperan cubrir para dinero, y hoy solo está cubierto para disponibilidad (habitaciones), no para pagos/cargos.

Causa raíz probable: el único test de concurrencia con `Promise.all` (`tests/adversarial/reserva-concurrencia-y-limites.spec.ts:45-56`) se escribió para probar el candado de `book_availability`, y se asumió (sin prueba) que cubría también la idempotencia porque ambas viven en el mismo endpoint.

### [ALTO] `npm test` (el comando canónico) no ejecuta las pruebas adversariales ni las E2E, y no existe `.github/workflows/ci.yml` en ningún lugar del repositorio
`package.json:8` (`"test": "npm run test:unit && npm run test:integration"`) — `docs/auditoria/RUBROS.md` cita `.github/workflows/ci.yml` como parte del rubro; `docs/ARQUITECTURA.md:357` lo incluye en la estructura de carpetas propuesta

Escenario: `find` sobre todo el repositorio (`find . -path "*.github/workflows*"`) no devuelve ningún archivo — no hay pipeline de CI configurado todavía, en ningún branch ni worktree. El script `test` de `package.json` (el que correría cualquier hook `pre-push`/CI que se agregue después, y el que un desarrollador corre por default) omite `test:adversarial` y el E2E de Playwright por completo; hay que saber invocar `npm run test:adversarial` a mano. Las pruebas de aislamiento entre tenants (`aislamiento-tenant-hotel.spec.ts`), de escalada de rol (`roles.spec.ts`) y de doble-cobro/sobreventa (`reserva-concurrencia-y-limites.spec.ts`) — exactamente las que este dominio no puede permitirse perder — no corren si alguien solo ejecuta `npm test` antes de un commit o un merge.

Consecuencia: una regresión de aislamiento entre hoteles o de escalada de rol puede mergearse sin que ningún gate automático la detecte, porque no existe el gate y el comando "estándar" no cubre esas 28 pruebas. Esto es actualmente el estado real detrás del ancla "6+ si la suite es grande y verde pero hay zonas de dinero o disponibilidad sin arnés" y del techo "8+ si...el CI corre en cada push" del propio rubro: hoy el CI no corre en ningún push porque no existe.

Causa raíz probable: el proyecto está en etapa H2 (según los comentarios de encabezado de los archivos); el pipeline de CI es trabajo pendiente de un hito posterior, pero no está declarado como tal en ningún documento de seguimiento que yo haya encontrado (no hay entrada en `docs/BLOQUEOS.md` sobre la ausencia de CI).

### [MEDIO] El cálculo de total de reserva no valida que exista tarifa para cada noche — una noche sin `rate_plan` se cobra como $0 en silencio
`apps/api/src/routes/reservas.ts:171-175`

Escenario: `totalAmount += rateRows[0] ? Number(rateRows[0].price) : 0;` — si para una fecha dada no existe fila en `rate_plan` (tarifa no cargada, error de operación, o una reserva que cae fuera del horizonte de 30 días que siembra `packages/db/src/seed.ts:37/105-115`), la función no lanza error: simplemente suma 0 para esa noche y la reserva se crea igual, con `book_availability` ya habiendo decrementado el inventario de esa noche. `grep -rn "rate_plan" tests/` solo encuentra dos archivos y ninguno prueba el caso "sin tarifa para esa fecha".

Consecuencia: una reserva válida (habitación reservada, inventario decrementado) puede quedar con `total_amount` menor al real sin ningún error visible para el staff — el huésped se queda con una noche gratis y nadie lo nota hasta la conciliación.

Causa raíz probable: `rateRows[0] ? ... : 0` trata "no hay tarifa" como "tarifa es cero" en vez de como un error (`sin_tarifa`) que debería bloquear la creación de la reserva, igual que `book_availability` sí bloquea con `sin_disponibilidad`.
